# 论文数字化平台

面向论文服务业务的轻量工作台：把**客户线索与档案**、**在途与已结工单**、**写手资源**放在同一套流程里，并用总览页帮你看清「钱从哪来、活卡在哪、人够不够用」。

---

## 平台在解决什么

- **客户分散**：渠道、院校层次、专业方向、预算与截稿预期不一致时，仍能在同一档案里沉淀，避免反复问同一件事。
- **工单与客户脱节**：系统强制「先有客户、再开工单」，新建工单时会自动带入与客户档案一致的信息，减少录错与漏项。
- **交付与结算看不清**：单笔工单可区分报价、回款、应收、成本与利润，总览上再汇总，方便对账与评估单子质量。
- **写手资源难调度**：写手池单独维护，可看负载与经验结构，和具体客户解耦，便于派单与长期合作管理。

## 业务模块说明

### 总览（经营视角）

从「老板或运营负责人」视角汇总当前盘子里的情况，例如：

- **钱**：总收入、已回款、应收账款、利润估算（在口径一致的前提下看趋势与异常单）。
- **活**：活跃工单规模、工单在各阶段的分布（便于发现卡在报价、撰写还是审改）。
- **结构**：自接与转包占比、服务类型分布、客户来源结构——用来判断渠道质量与产品结构是否要调整。
- **人**：写手池整体负载、平均表现与结清单量等，辅助判断要不要扩人、要不要控单。

支持按条件筛选后再看上述指标，便于按时间段、某类业务做复盘。

### 论文客户（档案中心）

客户是业务的入口。档案侧适合持续补齐：

- **是谁、从哪来**：称呼、常用联系方式、获客渠道。
- **背景与偏好**：院校类型与层次、学校与专业、学业阶段、风险感知（便于后续沟通策略）。
- **意向单信息**：倾向的题目方向、服务类型、期望截稿与预算区间、沟通备忘与最近联系时间。

**工单不会脱离客户凭空创建**：在客户详情或列表中一键生成工单，弹窗里会预填与客户档案重叠的字段，提交前仍可修改，保证「客户画像」和「履约单据」一致。

### 论文工单（履约与结算）

工单承载从接触到结清的全过程，便于运营与交付协同：

- **来源**：区分**自接**与**转包**，便于分别看利润空间与成本结构（转包单通常更需盯成本与利润）。
- **进度**：从线索、报价、撰写、审改、交付到售后等阶段，可在列表与看板中查看与筛选；支持按标题等关键词搜索，快速定位某一单。
- **交付要素**：题目、服务类型、打包方式、指派的写手、内外部截稿、紧急程度等。
- **财务字段**：成交金额、已结算、应收、成本、利润与回款状态，支持后续对账与经营分析。

工单支持在列表中**编辑与删除**（删除前请确认业务上已无纠纷或未结款项）。

### 论文写手（资源池）

写手与客户档案分开管理，强调「资源池」而非「某一单的附属」：

- **能力与标签**：擅长方向、当前忙闲状态、可接单容量、历史评分与完稿率、平均周转天数等。
- **合作条款**：价格档位、负责人、结算方式、内部备注。

新增写手在写手页完成，便于随时扩充合作名单而不影响既有客户数据。

## 流程与协作规则（约定）

1. **先建客户，再开工单**：新客户必须先落档案，再进入履约。
2. **工单只能从客户上下文生成**：不在系统中提供「没有客户」的建单路径，避免客户与订单割裂。
3. **写手独立维护**：写手信息在写手模块维护；派单时在工单里关联具体写手即可。

## 历史 Excel 数据

主存储为 `data/thesis.db`。导入会写入 SQLite，并同步刷新 JSON 种子备份（空库首次启动仍可读 JSON）。

```bash
npm run import:history -- /path/to/workbook.xlsx
npm run repair:history -- /path/to/workbook.xlsx
```

## 本地开发

建议使用 **Node.js 20** 或更高版本。

```bash
npm install
npm run dev
```

浏览器访问 [http://localhost:3000](http://localhost:3000)，默认进入总览。

生产环境打包与启动：

```bash
npm run build
npm run start
```

### 开发环境异常（缓存）

若本地启动后页面报错、模块找不到等异常，多为开发缓存损坏。可依次尝试：停止开发服务 → 删除项目下的 `.next` 目录 → 重新执行 `npm run dev`。
